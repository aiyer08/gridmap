# Methodology: where the numbers come from

This is the document for a skeptical reader — someone who wants to check our
arithmetic rather than trust our copy. It describes what the app actually
computes today. Where we think a constant should change, that's tracked
separately in [`docs/science-review.md`](./science-review.md) rather than
silently baked in here, so this document never claims more rigor than the
running code has.

**What's verified below, and how:** every emissions factor is checked against
a named source with a link. Every implementation fact (lag times, correlation
coefficients, forecast horizons) is taken from the project's own code comments
and tests, which were themselves checked against the live EIA API in August
2026 — see `src/lib/grid/eia.ts`, `demand.ts`, `climatology.ts`, and
`snapshot.ts` for the primary sources. Anything we couldn't independently
verify is marked **(unverified)** rather than stated as fact.

always labelled as modelled, never presented as measured.

## 2. How a fuel mix becomes gCO₂e/kWh

For a given hour, the EIA-930 feed reports megawatt-hours generated by fuel
code for a balancing authority (BA) — e.g. `NG: 4,200 MWh, SUN: 1,800 MWh,
WAT: 600 MWh`. We:

1. Drop storage codes (`BAT`, `PS`, `OES`, `UES`) entirely. A battery moves
   energy, it doesn't make it — counting discharge at 0 gCO₂/kWh would
   understate the evening peak in exactly the regions (like CAISO) where
   batteries do the most evening discharging.
2. Clamp negative generation to zero. CISO reports negative `SUN` overnight
   (inverter self-consumption) and negative `BAT`/`PS` while charging; these
   represent consumption, not generation.
3. Multiply each remaining fuel's MWh by its lifecycle emissions factor (§3)
   and divide the total grams by the total MWh:

   ```
   gCO2PerKWh = Σ(MWh_fuel × factor_fuel) / Σ(MWh_fuel)
   ```

4. Where the exact EIA code is known (e.g. `GEO` for geothermal), we use its
   own factor rather than the coarser display-bucket factor — see §3.

This is an **average intensity**: total emissions from everything generated
that hour, divided by total generation. It is not a marginal intensity — see
§6 for why that distinction matters and when it could mislead you.

## 3. Emissions factors

We use **lifecycle** factors (construction, fuel extraction and supply chain,
not just the smokestack) rather than combustion-only factors, for the same
reason Electricity Maps does: it's the more complete accounting, and it's
what makes solar, wind and nuclear small-but-nonzero, which is both more
honest and easier to explain than "zero."

| Fuel | gCO₂e/kWh | Source |
|---|---|---|
| Coal | 820 | IPCC AR5 WG3 Annex III, Table A.III.2 ("Coal – PC", no CCS), median. [ipcc.ch/.../ar5_annex-iii.pdf](https://www.ipcc.ch/site/assets/uploads/2018/02/ipcc_wg3_ar5_annex-iii.pdf) |
| Natural gas | 490 | Same table, "Gas – Combined Cycle" median. **Caveat:** this is a combined-cycle-specific figure applied uniformly to all gas generation, including hours with a heavier peaking-turbine mix. See §7 and `docs/science-review.md` item 2 — this is the single biggest open question in the model. |
| Oil | 650 | **Not an IPCC AR5 figure** — AR5 Annex III has no dedicated oil category, because oil is under 2% of global generation. 650 gCO₂e/kWh is a commonly-cited figure from UK Parliament POST Note 268 (Oct 2006), [parliament.uk/globalassets/documents/post/postpn268.pdf](https://www.parliament.uk/globalassets/documents/post/postpn268.pdf), in the same ballpark as other secondary sources (~650–750). The code comment attributing all factors to AR5 is imprecise for this one row — see the science review. |
| Nuclear | 12 | IPCC AR5 Annex III, median |
| Hydro | 24 | IPCC AR5 Annex III, median |
| Solar (utility PV) | 48 | IPCC AR5 Annex III, median |
| Wind (onshore) | 11 | IPCC AR5 Annex III, median |
| Biomass (EIA code `BIO`) | 230 | IPCC AR5 Annex III bioenergy median |
| Other / unclassified (EIA codes `OTH`, `UNK`) | 300 | Not a literature figure — a deliberate placeholder between biomass (230) and municipal-solid-waste/waste-to-energy, which runs considerably higher in the literature. `OTH`/`UNK` is a genuine grab-bag (landfill gas, waste heat, unclassified units) with no single defensible factor, so this is an disclosed approximation rather than a citation. |
| Geothermal (EIA code `GEO`) | 38 | IPCC AR5 Annex III geothermal median. Reported by EIA as its own code but folded into the "Other" *display* bucket; we use 38 for the actual gCO₂/kWh math regardless of which bucket it's shown in, because bucketing it at 300 measurably overstates emissions on geothermal-heavy grids like CAISO. |

A `DIRECT_FACTORS` (combustion-only) table also exists in `src/lib/emissions.ts`
for a possible future "how we calculate" panel, but nothing in the running

## 4. How the 7-day forecast is built

The EIA publishes no forecast — only a year of hourly history. The grid is
strongly periodic (2 PM next Tuesday looks like 2 PM on recent Tuesdays far
more than it looks like 2 AM today), so the forecast is a **climatology**:
168 buckets, one per hour-of-week in the region's local time, each a weighted
average of up to a year of matching historical hours.

Each historical hour is weighted by two independent kernels, multiplied
together:

- **Recency** — exponential decay, ~90-day half-life. A grid's mix can move
  fast (a region can add a gigawatt of solar or batteries in a year), so a
  month-old hour tells us much more than the same hour a year ago.
- **Seasonality** — a Gaussian kernel on the *circular* distance between
  day-of-year, ~30-day standard deviation. July solar doesn't look like
  January solar, and the circular distance means a forecast for January 2nd
  still learns from late December, not just from the following November.

Sparse hour-of-week buckets (regions with less history, or unusual hours)
shrink toward a coarser weekday/weekend × hour-of-day prior, so no bucket is
ever left empty or wildly noisy from a handful of samples.

That climatology gives the whole week's *shape*, but it's a typical week, not
this week. Three live signals correct it, layered in this precedence order —
each stronger signal overrides the previous one where it's available, and
corrections decay back to pure climatology rather than stopping abruptly:

1. **Demand nowcast.** EIA's fuel-mix data lags 9–12 hours behind real time
   (measured live: CISO ~9h, PJM ~12h, ERCO ~11h), so it can't describe the
   current hour. EIA's `region-data` dataset is fresher: live demand (`D`)
   lags only ~1 hour, and the day-ahead demand forecast (`DF`) reaches
   13–16 hours out. In demand-driven grids, extra load is met by marginal
   fossil generation, so an unusually high demand hour tends to be an
   unusually dirty one. We fit that relationship per region (ordinary least
   squares on 90 days of residuals against each series' own climatology) and
   **only apply the correction where the fit earns it**: currently CISO
   (r=0.74), PJM (r=0.82) and ISNE (r=0.77) pass the bar; SPP (r=0.01) and
   ERCOT (r=−0.19) don't, because those grids are wind/solar-driven rather
   than demand-driven, and get no correction at all. This is refit from live
   data rather than hand-tuned per region, so it self-calibrates as a grid's
   own behavior changes. The correction is hard-clamped: the demand input is
   capped at ±30% deviation and the resulting intensity move at ±35% of the
   climatology value, so a data glitch can't produce an absurd number.

   One specific wrinkle: EIA's day-ahead forecast (`DF`) and its actual
   metered demand (`D`) are not always on the same basis. Measured over 337
   overlapping hours, PJM's `DF` tracks `D` to within 4.3% and ERCOT's to
   1.2%, but CISO's ran **17–30% below** actual demand. Feeding a biased `DF`
   straight into a model built on `D` would silently flip the sign of a
   correction — an 8%-below-normal-looking forecast on a day that was
   actually 10% above normal. So `DF` is used only for its *shape* (the
   hour-to-hour change from the most recent real reading), never its level:
   the forecast is anchored to the freshest actual `D` reading, and a
   constant bias in `DF` cancels out exactly.

2. **Electricity Maps live reading and forecast**, when a token is
   configured. This is an actual measured intensity rather than a demand
   proxy, so it overrides the demand nowcast outright wherever it's
   available — a live reading anchors "now" and decays (linearly, over
   ~30 hours by default) back to pure climatology, and Electricity Maps'
   own ~24h forecast overrides the climatology+demand blend for the hours it
   covers.

3. **WattTime** is deliberately *never* blended in. WattTime's MOER is a
   marginal-emissions signal; our series is an average-emissions signal.
   Silently averaging the two would produce a number that isn't honestly
   either one. Instead, WattTime's cleanliness percentile appears as an
   independent cross-check line ("WattTime independently ranks right now at
   X/100 for cleanliness") — see §6.

Practically: the first ~16 hours of the week can be conditioned on real
demand and (if configured) real measured intensity; everything past that is
the grid's typical pattern for that hour of the week, with no knowledge of
whether next Thursday will be unusually windy or hot. Every hour in the
series is labelled with a confidence (`high`/`medium`/`low`) and a source
(`live`/`forecast`/`blend`/`climatology`) so the UI never overstates its own
certainty.

## 5. How savings are computed

- **Baseline is "running it right now,"** not the week's dirtiest hour.
  Comparing against the worst possible moment would inflate every savings
  number and make the comparison meaningless.
- A run's energy is split across the clock hours it spans (e.g. a 90-minute
  cycle starting at 2:00 PM counts as 1.0 hour of the 2 PM intensity and
  0.5 hour of the 3 PM intensity), so `gramsCO2 = kWhPerRun × energy-weighted
  average intensity across the run`.
- Recommendations are only offered within a **48-hour horizon**
  (`RECOMMEND_HORIZON_HOURS`), even though the full week is displayed for
  planning. This exists because the forecast's realism decays with distance:
  live demand and the day-ahead forecast condition roughly the first 16
  hours, so recommending "next Saturday" over "tonight" compares a measured
  today against an idealized someday. (This was a real bug during
  development — the app once told a Sunday-afternoon visitor to wait until
  the following Saturday for a 32% saving, which is not useful advice for
  someone holding a basket of laundry.) The week-at-a-glance view
  (`dailyBest`) still covers the full 7 days, since planning around a busy
  Tuesday is legitimately useful even past the 48-hour recommendation
  window — it's just not pushed as an urgent "wait for this" suggestion.
- Among near-tied windows, we prefer the earlier one and avoid stacking every
  suggestion on the same day, so a person gets genuinely different options
  rather than three flavors of "Tuesday at 3 AM."

## 6. Average vs. marginal emissions — the honest caveat

**What we do:** every number in this app is an *average* emissions
intensity — total grams of CO₂ from everything generated that hour, divided
by total generation.

**Why:** average intensity is the only signal that's freely published, in a
consistent form, for essentially every US grid region, straight from EIA's
public data. It's also far easier to explain honestly to someone who has
never heard the phrase "carbon intensity" before. A *marginal* emissions
rate (MER) — what the very next kilowatt-hour of demand actually causes,
because of which specific plant ramps up to supply it — is the metric that's
academically correct for a load-shifting decision like "should I run my
dishwasher now or in three hours." Services like WattTime's MOER (Marginal
Operating Emissions Rate) are built specifically to estimate this.

**When it could mislead:** average and marginal intensity are calculated
completely differently, and they can point in different directions. The
foundational study on this, Siler-Evans, Azevedo & Morgan, *"Marginal
Emissions Factors for the U.S. Electricity System"* (Environmental Science &
Technology, 2012 — [PDF via WattTime](https://watttime.org/wp-content/uploads/2023/11/Marginal-Emissions-Factors-for-the-US-Electricity-System_April-2012.pdf),
[PubMed](https://pubmed.ncbi.nlm.nih.gov/22486733/)), found that a system
average emissions factor "could be misleading" because a change in demand
doesn't act on every generator proportionally — it's specifically the
marginal generator's intensity that determines the real effect of using (or
avoiding) a kilowatt-hour. As one concrete illustration from that
literature, an identical efficiency measure was estimated to avoid roughly
70% more CO₂ in the Midwest than an equivalent measure in the West, a gap
invisible to an average-intensity comparison within either region alone.
WattTime makes the point even more directly with a scenario ([Average vs.
marginal emissions](https://watttime.org/data-science/data-signals/average-vs-marginal/)):
a new load added to a grid with abundant hydropower can, on paper, look
low-carbon by the average metric, while in reality it causes a fossil
peaking plant to ramp up in response — meaning the *marginal* effect of that
load was to increase emissions, the opposite of what average intensity
implied.

**How big the error typically is, honestly:** we could not find a
peer-reviewed source that gives a single clean "X% of hours" or "average and
marginal disagree in sign Z% of the time" figure for the whole US, and we
did not want to invent one. What the literature does establish is (a) the
two measures are calculated from different information and can diverge
sharply by region and by hour, (b) the direction of the gap is *not*
consistent across regions (the Midwest/West comparison above went one way;
WattTime's hydro-plus-peaker example goes the other), and (c) the mismatch is
worst specifically in grids with a lot of "always-on" low-carbon generation
(hydro, nuclear) sitting next to a fast-ramping fossil margin — exactly the
situation where "the average looks clean" and "the marginal plant is dirty"
can both be true at once. We treat this as a real, structural limitation of
every average-intensity tool (ourselves included), not a rounding error, and
say so in the app's own limitations panel.

## 8. Limitations

- **ZIP → grid region is approximate.** Utility service territories don't
  follow postal boundaries, and several states are split across multiple
  grid operators. `matchedBy` and `approximate` on every `RegionInfo` record
  exactly how we got there (hand-checked ZIP5 table, ZIP3 prefix, state
  centroid, or a manual pick) — see `src/lib/region/resolve.ts`.
- **Average, not marginal, emissions.** See §6.
- **The gas factor is technology-blind.** A single 490 gCO₂e/kWh factor is
  applied to every megawatt-hour reported under EIA's `NG` code, whether it
  came from an efficient combined-cycle plant or a peaking turbine — and
  EIA's hourly fuel-type data has no finer breakdown to work from. Peaking
  turbines run disproportionately during the evening demand ramp, which is
  precisely the window this app is telling people to avoid — see
  `docs/science-review.md` item 2 for the numbers.
- **The fuel mix runs 9–12 hours behind.** The current hour is nowcast from
  live demand (§4) or, without an EIA key or Electricity Maps token, modelled
  from historical pattern rather than measured directly. The app's UI states
  which one applies for any given hour.
- **Beyond ~16 hours, it's a pattern, not a prediction.** The far end of the
  week reflects the grid's typical shape for that hour and day of the week —
  it has no weather forecast and doesn't know if next Thursday will be
  unusually windy or hot.
- **Appliance energy is a typical-use estimate**, not a meter reading. The
  percentage savings between two windows still holds even if your specific
  appliance's total is higher or lower; only the gram totals shift.

## 9. How to check us

The EIA data behind all of this is public. To pull the same raw hourly
generation-by-fuel-type rows the app uses for a region (CISO here), get a
free key from [eia.gov/opendata/register.php](https://www.eia.gov/opendata/register.php)
and run:

```bash
curl -g "https://api.eia.gov/v2/electricity/rto/fuel-type-data/data/?api_key=YOUR_KEY&frequency=hourly&data[0]=value&facets[respondent][]=CISO&start=2026-08-20T00&end=2026-08-23T00&sort[0][column]=period&sort[0][direction]=desc&offset=0&length=200"
```

**The `-g` flag matters.** Without it, curl treats `[0]` and `[]` in the URL
as its own glob/range syntax (the same feature that lets `curl
"http://x/{a,b}"` fetch two URLs in one command) and will silently mangle
`data[0]` and `facets[respondent][]` instead of sending them literally.
`-g` (`--globoff`) turns that off so the brackets reach the API untouched.

To see the live demand and day-ahead forecast that the nowcast in §4 is
built from, swap the path and add a `type` facet:

```bash
curl -g "https://api.eia.gov/v2/electricity/rto/region-data/data/?api_key=YOUR_KEY&frequency=hourly&data[0]=value&facets[respondent][]=CISO&facets[type][]=DF&start=2026-08-23T00&end=2026-08-24T00&sort[0][column]=period&sort[0][direction]=desc"
```

(`type=D` for actual demand, `type=DF` for the day-ahead forecast.)

You should see the response lag behind wall-clock time by roughly a half day
for the fuel-type endpoint and about an hour for `type=D` — that's the same
lag described in §4, not a bug in either the API or this app.
